# 第 13 回 テストの戦略

> 所要時間の目安: 3 時間 / 前提: 第 9 回

## この回のゴール

- この道具のテストが、**どの層を、どの方法で**確かめているかを説明できる。
- **時計・乱数・外部プログラム**を差し替えられる設計と、その利点が分かる。
- **不安定なテスト(flaky)**の原因を探す手順と、実際に起きた例を説明できる。
- Python(pytest)と JavaScript(node:test)の**両方で**、新しいテストを足せる。

## 1. 全体の地図

## 2. 差し替えられる設計

テストしやすさは、**設計の段階**で決まります。

### 2.1 時計を引数にする

```python
# 実行できる
from chapterlens.live_sessions import MAX_SESSIONS_PER_USER, LiveSessionError, LiveSessions

sessions = LiveSessions(clock=lambda: 100.0)        # 時計が止まっている(分解能が粗い環境の再現)
ids = [sessions.push("u", None, [], None)[0] for _ in range(MAX_SESSIONS_PER_USER)]
sessions.push("u", ids[0], [], None)                # ids[0] を使う → いちばん古いのは ids[1]
sessions.push("u", None, [], None)                  # 上限なので、1 つ捨てられる
for i, sid in enumerate(ids):
    try:
        sessions.push("u", sid, [], None)
        print(f"セッション {i}: 生きている")
    except LiveSessionError:
        print(f"セッション {i}: 捨てられた")
```

```text
# 出力
セッション 0: 生きている
セッション 1: 捨てられた
セッション 2: 生きている
セッション 3: 生きている
```

- `LiveSessions` は、時計を `clock` 引数で受けます(既定は `time.monotonic`)。テストでは**時間を止めたり、進めたり**できる。
- **実際に起きた不具合**: 「いちばん古いセッションを捨てる」を、時刻の大小で決めていました。Windows の `monotonic` は分解能が約 15 ms で、**短時間に作ると時刻が同じ**になり、同点は**ランダムなセッション ID の順**に。結果、**新しいものが捨てられる**ことがあり、テストも**まれに**失敗しました。
- 直し方: 時計ではなく、**単調に増える連番**(`itertools.count`)で順序を決める。上の例は、時計が止まっていても、決まった結果になります。

### 2.2 偽物を渡す

- サーバーの音声認識は、`Config(asr_fn=...)` で**偽の関数**を渡せる(本物の faster-whisper を呼ばない)。
- 拡張の `fetch` は、`CaptureSession(deps={fetch: …})` で渡す。`offscreen.js` だけが本物の `fetch` を渡す。
- レート制限は、`clock` を差し替えて**待たずに**確かめる(第 9 回)。

## 3. 実際のサーバーで確かめる

HTTP のテストは、**モックでなく本物のサーバー**を立てます(`create_server(cfg, port=0)`)。ヘッダ・ステータス・本文が、実際の通信で確かめられます。

```python
# 抜粋ファイル: engine/tests/conftest.py
@pytest.fixture
def env(tmp_path):
    cfg = Config(home=tmp_path, token=ADMIN, asr_fn=lambda *a, **k: None)
    httpd = create_server(cfg, port=0)
```

- **フィクスチャ**(`@pytest.fixture`)は、テストの準備と後片付けをまとめる。`yield` の前が準備、後ろが後片付け。
- `tmp_path` は、テストごとの**空の一時フォルダ**。実際の `~/.chapterlens` に触れない。

## 4. 「通らないはずのもの」を確かめる

守りのテストは、**拒否されること**を確かめます。

- 利用者が `role: admin` と名乗っても、管理者の経路は `403`。
- 余計な項目(`transcript`)を付けた共有は、拒否。
- 許可リストに無い経路は、通信しない(`fetch` が 0 回)。
- 停止された利用者と、不明な token は、**同じ `401`**。

これらは、**機能が動くこと**のテストより、見落とされやすく、壊れたときの被害が大きい。

## 5. 不安定なテスト(flaky)

「たまに落ちる」テストは、放置すると、**本当に落ちたときに無視される**ようになります。見つけたら、原因を調べます。

1. **再現する**: 同じテストを何度も回す(`for i in 1..8: pytest -x`)。
2. **時間・順序・乱数**を疑う: 時計の分解能・辞書や集合の順序・ランダムな ID・スレッドの順序。
3. **原因が見えないときは、決定的にして再現する**: 時計を止める・乱数の種を固定する。
4. 直したら、**その原因だけを再現する専用のテスト**を足す(上の例)。

文書の実行例も同じで、**毎回変わる出力**(ランダムな token・一時フォルダのパス)を書くと、2 回走らせる検査で落ちます(この講義でも、実際に落ちて直しました)。

## 6. JavaScript のテスト(node:test)

```javascript
// 抜粋ファイル: extension/test/core.test.mjs
import { test } from "node:test";
import assert from "node:assert/strict";
```

- 依存なし(Node の標準機能だけ)。`npm test` で全部走る。
- **別の世界のオブジェクトは `deepEqual` できない**: 偽の chrome の中(`vm`)で作った配列・オブジェクトは、外の世界と**プロトタイプが違う**ので、`assert.deepEqual` が失敗する。`JSON.parse(JSON.stringify(x))` で複製して比べる(`helpers.mjs` の `clone`)。
- 偽の DOM(`fakedom.mjs`)は、**使う範囲だけ**を持つ最小のもの。外部ライブラリ(jsdom)を入れない代わりに、増やす手間がある。

## 7. 確認の範囲(正直に)

**テストが通っても、保証されないもの**があります。

| 確認できたもの | 確認できていないもの |
|---|---|
| 検出・ダイジェストの正しさ、Python と JS の一致(実データ含む) | **拡張を本物の Chrome に読み込んでの動作**(`tabCapture`・offscreen・popup) |
| サーバーの認証・分離・制限・監査 | **本物のライブ配信**での精度・遅れ |
| 画面の操作(偽 DOM・モックのページ) | 人の「重要」との一致(ダイジェスト) |

**本物の環境でしか確かめられないもの**を、README に書き、利用者の操作で確かめる。**テストの数を、品質の証拠にしない**。

## 確認問題

1. HTTP のテストで、モックでなく本物のサーバーを立てる利点は何ですか。
2. 時計を `clock` 引数で受ける設計の利点を 2 つ挙げてください。
3. 「古いものを捨てる」を時刻で決めていたとき、なぜ新しいものが捨てられることがありましたか。
4. `vm` の中で作った配列を `deepEqual` で比べると、なぜ失敗しますか。
5. 文書の実行例に、ランダムな値を出力してはいけない理由は。

## 解答

1. ヘッダ・ステータス・本文・文字コードなど、**実際の通信**の細部まで確かめられる。モックでは、モックに都合のよい前提がテストを通してしまう。
2. 実際に待たずに、時間の経過を**速く確かめられる**。時間が絡む不具合(同時刻・窓の境目)を**決定的に再現**できる。
3. 分解能の粗い時計では、短時間に作った複数のセッションの時刻が**同じ**になり、同点を**ランダムな ID の順**で並べたため。
4. 別の実行環境(realm)で作られたオブジェクトは、`Array.prototype` が別物で、厳密な比較(`strict`)で**型が違う**と判定される。
5. 実行例は、書かれた出力と**一致するか**を 2 回の実行で検査する。毎回変わる値は、必ず食い違い、検査が落ちる。

## まとめ

- テストは層ごとに方法を変える。純粋なロジックは速く、HTTP は本物のサーバーで、外部プログラムは実物で。
- 時計・偽物の関数を**引数で渡せる**設計が、テストを速く確実にする。
- 「拒否されること」を確かめる。守りのテストは、機能のテストより大切なことがある。
- 不安定なテストは放置しない。原因(時間・順序・乱数)を決定的にして再現する。
